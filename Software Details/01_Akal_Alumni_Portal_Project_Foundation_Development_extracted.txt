1. Purpose of This Development Document

This document defines the foundation that must be completed before implementing individual functional modules of the Akal University Alumni Portal. It establishes the project architecture, technology stack, roles, coding rules, folder structure, security principles and development sequence.

The goal is to create a clean, scalable and production-ready system from the beginning rather than building disconnected features and restructuring the project later.

2. Final Product Definition

The system will be a centralized alumni networking and university engagement platform. Public users can browse approved content without login. Authenticated students and alumni receive personalized features. Admins manage operational content and users. The Super Admin has complete control over system settings, public visibility, permissions and all modules.

4. System Architecture

The system will follow a frontend/backend separation:

React Frontend → REST API → CodeIgniter 4 Backend → MySQL Database

The frontend must not directly connect to MySQL. All database access must happen through the CodeIgniter 4 backend/API.

8. Super Admin Control Model

Super Admin must have database-driven control over what is visible on the public portal and which features are enabled. This should not depend on hard-coded frontend conditions.

Enable/disable public modules.

Show/hide navigation menu items.

Manage homepage sections.

Control public alumni profile fields.

Publish/unpublish news, stories, gallery, events and other content.

Manage public content order where required.

Manage Admin accounts and permissions.

Manage system settings.

View audit logs.

Enable/disable future modules such as messaging or donations.

10. Database Foundation Principles

Use migrations instead of manually creating production tables.

Use foreign keys where appropriate.

Use created_at and updated_at consistently.

Use status fields for activation workflows.

Prefer soft deletion for important records.

Use indexed columns for search/filter operations.

Do not store plain-text passwords.

Keep authentication users separate from profile-specific data.

Keep public visibility and system settings in database-driven configuration where appropriate.

11. API Standards

Use RESTful URL structure.

Return consistent JSON responses.

Use HTTP status codes correctly.

Validate all request data on the backend.

Never trust role/user IDs sent by the frontend.

Derive the authenticated user identity from the authenticated session/token.

Use pagination for large lists.

Return only fields permitted for the requesting role.

Keep API versioning available for future mobile applications.

11.1 Standard API Response

{  "status": true,  "message": "Request successful",  "data": {},  "errors": []}

12. Security Foundation

HTTPS in production.

Strong password hashing.

Authentication filters on protected routes.

Role and permission checks on backend.

Input validation.

SQL injection protection through CodeIgniter query builder/parameterized queries.

CSRF protection where applicable.

Secure file upload validation.

Rate limiting for authentication endpoints.

Audit logging for critical administrative operations.

Do not expose internal server errors, SQL queries or credentials.

Do not expose private alumni fields through public API responses.

13. Development Rules

Develop one feature at a time.

Explain the feature flow before implementation.

Do not start the next feature until the current feature is tested/confirmed.

When a file changes, provide the complete file code during implementation.

Do not overwrite or break existing functionality.

Follow CodeIgniter 4 MVC/API standards.

Use reusable React components instead of duplicating UI code.

Keep business logic out of React components where it belongs in the backend.

Use database migrations and seeders.

Keep production-ready validation and error handling from the beginning.

Use consistent naming conventions.

Do not hard-code public visibility rules that Super Admin should control.

15. Definition of Done for Each Feature
